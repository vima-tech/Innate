## 0. 结论

Innate 现在做的是「保存并给保存物计数」，不是「让知识经实践晋升」。65 条 active 里，61 条确实是自动晋升上来的，不是靠你强调保存；但晋升机制分不清知识和汇报，于是晋升上来的主要是项目进展汇报和空泛格言，真正有增量的通用知识约 6 条。

这不是调参能解决的问题。根因有六个，其中三个 Codex 已指出，另外三个是本次新发现：**规则在错误的时机被召回**、**规则从错误的素材里诞生**、**系统不知道自己在哪个项目里**。我赞同 Codex 的方向（经历 / 规则 / 验证三分、验证驱动晋升、反例驱动修订），并在此基础上补三块：动作时召回、确定性的规则出生机制、两级成熟度。

推荐做破坏性重构：新 schema 大版本，旧库在副本上重建，不继承无法证明的成熟资格。

## 1. 先回答你的三个问题

### 1.1 active 的来源：不是你强调保存的，是自动晋升的

| 状态原因 | 条数 | 含义 |
|---|---:|---|
| `repeated_success` | 50 | 被标记「使用 + 任务成功」≥2 次后自动晋升 |
| `sustained_usefulness` | 11 | 弱晋升：被选 ≥20 次、用过 1 次、满 14 天 |
| `init:captured` | 4 | 捕获时直接生效 |

59 条蒸馏产物全部没有「提名保存」标记，55 条来自 hook 自动通道。所以你的担心不成立：它们确实是「从底层一步步升上来的」。问题在于这条晋升路径本身不检验内容。

### 1.2 其中有多少是通用知识：约 6 条

逐条人工归类（主观判断，可在本机按短 ID 复核）：

| 类别 | 条数 | 例子 |
|---|---:|---|
| 纯项目进展汇报 | 24 | `9977945a` 首页统计改成「5+ 厂区」；`f691a280` 项目J 跑通 49 个单测 |
| 空泛通用格言 | 23 | `13d0dcd7` 后台任务完成后要看日志；`7a4cd583` 部署后要验证 |
| 汇报里夹着真洞察 | 7 | `628fb331` 页头被裁的真正根因在卡内一层；`085c820d` 发布流程的 6 个坑 |
| 有真实增量的通用知识 | 6 | `39de8f52` Chromium 121+ 设了标准滚动条属性就忽略 `::-webkit-scrollbar`；`1c5d7ec3` 按名字 kill 进程会误杀自身 |
| 你指定的规则 | 3 | `1a211dfb` 防过度设计；`8dba32a6` 文档标日期 |
| 项目事实或操作步骤 | 2 | `38af2cde` 用 `cargo build --release` 构建 innate |

两个数字值得注意：纯汇报几乎全部来自 LLM 失败时的启发式兜底（31 条兜底产物里约 24 条）；格言几乎全部来自 LLM 蒸馏（28 条里约 23 条）。两条产出路径各自制造了一种噪声。

### 1.3 为什么汇报也能晋升

晋升只看「这条 chunk 被 agent 标记用过、且那次任务整体成功」。一条「首页改完了」的汇报，被同项目后续两次任务作为背景读到、agent 顺手标了用过，就满足条件。没有任何一步问「它建议的动作是什么、做了之后观察到了什么」。

## 2. 独立诊断：六个根因

| # | 根因 | Codex 是否指出 | 关键证据 |
|---|---|---|---|
| G1 | 经历、规则、用户指令共用一张表和一套生命周期 | 是 | 1.2 的归类 |
| G2 | 规则从错误的素材里、以错误的方式诞生 | 部分 | 见 2.1 |
| G3 | 晋升信号是自述的「用过」，没有动作和观察 | 是 | 见 2.2 |
| G4 | 规则只在用户提问时、按提问原话召回一次 | **否** | 见 2.3 |
| G5 | 系统没有项目身份 | **否** | 见 2.4 |
| G6 | 一个 confidence 同时承担相关性、可信度、新鲜度 | 是 | 草案 3.6 |

### 2.1 G2：规则的出生方式

- **素材是完成汇报。** Stop hook 取的是「最后一条助手回复的前 400 字」（`hook.rs`），天然是「已完成 X」式汇报。真正有学习价值的部分（报错、试错、找到根因、验证修复）在 transcript 的工具调用里，从未被采集。
- **一条日志就能生一条规则。** 9 月每天新增约 107 条候选，70% 从未被召回。单条日志不足以判断什么是可复用的，LLM 只能二选一：照抄汇报，或写一句放之四海皆准的格言。
- **结果**：素材偏汇报 + 单例即生 = 汇报和格言两种噪声，正是 1.2 看到的分布。

### 2.2 G3：验证供给严重不足

近 30 天：

| 指标 | 数值 |
|---|---:|
| 提问触发的 trace | 2,931 |
| agent 明确标记「用过」的 trace | 167（5.7%），日均 7.6 次 |
| 生成后在两个不同日子被明确使用且任务成功的 chunk | 25 |

这 25 条的「用过」都是自述，没有动作和观察。若按 Codex 草案的门槛（生成后两次独立验证、附观察、其中一次跨项目），今天的反馈量每月只能支撑个位数晋升。**只收紧门槛而不增加验证供给，活知识库会变成死知识库。** 这是本方案相对草案最重要的补充。

### 2.3 G4：召回时机错了（本次会话的实证）

今天我写了一个等待循环 `until ! pgrep -f 'innate.* evolve --trigger'`，它匹配到了自己的 shell 命令行，卡住 10 分钟。库里正好有一条 active：`1c5d7ec3`「按名字 kill 进程时，宽匹配会误杀调用脚本自身」。它没有出现，因为：

- 召回只在用户发消息时按原话触发一次，而你的原话是「开始优化，同时注意安全问题」。
- 这类操作知识在 agent **即将执行某条命令**或**刚看到某个报错**的时刻才有用。

同一个例子还暴露了规则不完整：它建议「先用 `pgrep` 找 PID 再 kill」，而 `pgrep -f` 同样会匹配调用者自己。这正是一次应当收窄规则的反例，现在的系统只会继续给原文累加使用次数。

### 2.4 G5：没有项目身份

`episodic_log` 和 `chunks` 都没有项目字段；hook 读取 `cwd` 只用来拼 SessionStart 的查询词。于是：

- 「跨项目验证」在现有数据上无法计算。
- 项目事实无法按项目隔离，只能和通用规则在同一个池子里竞争。
- `context_key` 在 hook 路径上退化成提问文本的哈希（30 天 2,903 次召回产生 2,253 个 key），情境校准学不到任何东西。

## 4. 目标设计

### 4.1 四类对象

| 对象 | 内容 | 是否进默认召回 |
|---|---|---|
| 经历 Episode | 一次任务里的一段「波折」：信号、尝试、观察、修复、验证，带项目身份。可以很具体 | 否，只在明确查询历史时检索 |
| 规则 Rule（带版本） | 适用信号、建议动作、预期观察、已知边界、已验证范围 | 是，按成熟度分层 |
| 验证 Validation | 某规则某版本在某任务中：是否采用、观察到什么、支持 / 反驳 / 不适用 | 否，用于晋升与展示 |
| 指令 Directive | 你明确要求遵守的规则与偏好 | 是，标注「用户指定」，不计入经验成熟度 |

现有 `chunks` 的一张表承担了全部四种角色，这是 G1 的直接体现。

### 4.2 规则怎么诞生：复现驱动，而不是单例驱动

- **经历采集是确定性的。** 从 transcript 的工具调用序列里切出「波折片段」：出现报错或非零退出 → 若干次尝试 → 恢复成功 → 有验证动作。这一步不调 LLM，可复现，符合你定下的被动捕获原则。纯完成汇报没有波折，不产生经历。
- **规则的出生条件是复现。** 当两个以上经历在信号上聚到一起（相同报错类型、相同命令或 API、相同症状，按实体重叠与向量相似度做确定性聚类），才生成候选规则。复现本身就是「不止一次有用」的初步证据，也天然把产量从每天约 107 条压到少量。
- **单例例外。** 一个经历如果含完整的「失败 → 找到根因 → 修复 → 验证」且根因反直觉（例如 Chromium 滚动条那条），允许单例生成候选，但标注「单例」。
- **LLM 只负责把聚类写成规则文本**，并执行 Codex 草案 5.2 的质量门。LLM 不可用时，聚类照常进行，候选的文字生成排队等待。

### 4.3 规则的形态：正文通用，信号具体

这一点调和了 prompt v4 和 v5 的矛盾：

- v4 要求剥离一切标识符，产出的格言 70% 从未被召回。
- v5 要求保留标识符和项目名，产出的内容更具体，但又回到了项目相关。

规则拆成两部分：

- **信号**：具体、可检索，用你的语言，必要时中英双写。比如 `pgrep -f`、`pkill -f`、「等待循环卡住」、`UNIQUE constraint failed`。召回按信号做词法与实体匹配。
- **动作、预期观察、边界**：通用表述，不含项目名、提交号、业务数值；具体案例留在经历里，通过来源关系可展开。

### 4.4 两个召回时机

| 时机 | 触发点 | 匹配方式 | 注入条件 |
|---|---|---|---|
| 提问时 | UserPromptSubmit（现有） | 语义 + 词法 | 默认只返回成熟规则 + 至多 1 条候选试用 |
| 动作时（新） | PreToolUse：即将执行的命令；PostToolUse：报错输出 | 只做本地词法 / 实体匹配，不走网络 | 仅强匹配才注入，每次至多 1 条 |

**白话说明。** 现在 Innate 只在你发一句话时查一次库，用的是你这句话的字面内容。可 agent 真正犯错的时刻，往往是它自己在干活的中途：准备敲一条命令，或者刚看到一段报错。动作时召回就是在这两个时刻再查一次：

- **敲命令之前**：agent 准备执行 `pgrep -f 'innate.* evolve'`，Innate 用这条命令的文字在本地规则里找，发现「`pgrep -f` 会匹配到调用者自己」这条规则，就在命令执行前把它塞给 agent。
- **看到报错之后**：命令输出 `UNIQUE constraint failed`，Innate 用这段报错去找，找到「回收租约时撞唯一索引」这类规则，塞给 agent。

它只在本机做文字匹配，不调网络，所以几乎不增加等待；只有匹配得很准时才出现，每次最多一条。顺带的好处是，命令执行的结果（成功、报错、卡住）会被自动记下来，成为这条规则「管不管用」的证据。

动作时召回是让验证供给上来的关键：规则在动作前出现，动作的结果（退出码、输出、是否卡住）就是现成的观察。停用现在的 SessionStart 召回（9 月 473 次，0 次被使用）。

### 4.5 验证：让证据自动落地

- 反馈分五类，沿用 Codex 草案 5.5：看见、采用但结果未知、支持、反驳、不适用。只有「支持」且附观察才计入验证。
- **动作时注入的规则**：记录注入 → 下一次工具调用 → 工具结果。agent 只需确认是否采用；「观察到了什么」由系统从工具结果中取，不靠 agent 转述。
- **提问时注入的规则**：保留 agent 收尾时的结构化 record，但格式压到最短（规则 ID + 采用与否 + 一句观察）。
- 独立性：同一会话、同一任务的重复记录只算一次；规则生成所依据的经历不能再算作它的验证。

### 4.6 两级成熟度

| 级别 | 条件 | 召回表现 |
|---|---|---|
| 候选 | 刚诞生，或验证不足 | 只占试用位，明确标注未验证 |
| 已验证 | ≥2 次生成后的独立验证，无未决反例 | 默认召回，展示已验证范围（哪些项目、哪些条件） |
| 可迁移 | 已验证，且至少 1 次验证来自来源以外的项目 | 默认召回，排序优先 |

> **2026-09-24 用户决定**：成熟以跨项目为准，即只有「可迁移」一级算成熟；「已验证」但仅限单项目的规则停在候选。采纳 Codex 草案 5.3 的立场。

### 4.7 反例与修订

沿用 Codex 草案 5.6：反例暂停成熟资格 → 判断是越界使用、规则不成立还是材料有误 → 需要时生成新版本，旧证据逐条重新判断，不自动继承。`1c5d7ec3` 就是现成的第一个修订样例。

### 4.8 安全

经历会含有大量敏感原文。本次已把脱敏接到所有入口和外发点（见第 6 节 S0）。新对象模型下，经历仍然只在本地，外发给 LLM 前统一脱敏；规则文本在质量门里再做一次敏感信息检查。

## 5. 迁移

- 在一致性副本上重建，旧库保留为历史与回滚点。
- 65 条 active 按 1.2 的归类处置：
  - 纯汇报 24 条 → 转为经历，不进规则。
  - 格言 23 条 → 进入候选队列；过不了质量门的保留淘汰原因。
  - 夹着洞察的汇报 7 条 → 原文转为经历，拆出候选规则。
  - 有增量的通用知识 6 条 → 候选，按可追溯证据重评，不直接成熟。
  - 你指定的规则 3 条 → 指令。
  - 项目事实 2 条 → 转为带项目身份的经历或项目笔记。
- 2,297 条 pending 全部转为候选或经历，交给新的复现聚类处理；绝大多数预计不会生成规则。
- 旧的成功计数不迁移为新验证；能追溯到带观察材料的记录可逐条重评。

### S1：地基（先做，破坏性）

- 记录项目身份：hook 与 MCP 带上 git 根目录或 `cwd`，写入经历与验证。
- 新 schema 大版本：经历 / 规则（带版本）/ 验证 / 指令四张表。
- 确定性的经历抽取：从 transcript 工具序列切出波折片段。
- 停止启发式兜底产出规则；LLM 不可用时只保存经历。
- 验收：一段「发布完成、测试通过」的会话产生 0 条规则；一段「报错 → 修复 → 验证」的会话产生 1 条经历。

### S2：规则的诞生与召回

- 复现聚类触发候选生成；LLM 只写规则文字并过质量门。
- 规则形态：信号具体、正文通用。
- 动作时召回（PreToolUse / PostToolUse，本地词法匹配）；停用 SessionStart 召回。
- 验收：`pgrep -f` 场景下，执行命令前能匹配出进程自匹配规则。

### S3：验证闭环

- 五类反馈、自动收集动作后的观察、独立性判定。
- 两级成熟度与晋升记录；反例暂停与版本修订。
- 验收：同一案例重复记录十次不能晋升；两次独立支持且无反例可以晋升，并能展开证据。

### S4：旧库重建与切换

- 副本重建、差异报告、按任务分组的留出评估，通过后切换正式库。

## 7. 衡量指标

主指标不再用 pending / active 比例或蒸馏产量：

| 指标 | 含义 |
|---|---|
| 默认召回中「可执行、可迁移规则」的占比 | 召回纯度 |
| 默认召回中一次性项目状态的占比 | 污染率，目标接近 0 |
| 每周新增有效验证数 | **验证吞吐**，新机制能否活起来的关键 |
| 候选从诞生到首次验证的中位时间 | 候选是否真的有机会被检验 |
| 成熟规则中有可追溯独立证据的比例 | 成熟度可信程度 |
| 反例出现后被暂停或修订的比例 | 纠错能力 |
| 同类错误复发率 | 最终价值 |
