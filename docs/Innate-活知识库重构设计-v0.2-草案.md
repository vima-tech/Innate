# Innate 活知识库：现状审计与重构设计

创建日期：2026-09-23  
状态：设计草案，未实施；不替代现行编码基线。  
依据：本机 `personal.db` 的一致性快照、当前工作树源码、v0.1.9 设计文档。统计口径为本次审计快照，不随后台进程后续写入变化。

## 1. 结论与产品目标

用户需要的是：从真实工作中自动积累经历，提炼可迁移的方法，通过后续实践验证、修正和晋升，形成越来越有用的通用知识库。

当前系统已经具有自动蒸馏和自动晋升，但其实际闭环更接近：

> 任务摘要 → 文本块 → 被召回和标记使用 → 计数、置信度上涨 → 同一文本变成 active。

缺失的关键环节是：**经历与知识分离、跨案例归纳、对具体规则的验证、反例驱动的内容修正**。因此“会自动晋升”成立，“晋升后代表已验证的通用知识”不成立。值得重构的是知识形成与成熟的机制，不是把晋升门槛继续调低。

“通用”不要求适用于所有技术栈。SQLite 并发写入、某浏览器标准属性与私有样式的冲突，都可以是通用知识；关键是换一个项目，同类条件下仍能改变决策。反过来，“发布完成”“某页面已修改”不是知识；“做完要检查”虽没有项目名，也未必有足够的新增价值。

## 2. 真实数据回答了什么

### 2.1 库的规模与 active 来源

| 状态 | captured | distilled | 合计 |
|---|---:|---:|---:|
| active | 6 | 59 | 65 |
| pending | 4 | 2,293 | 2,297 |
| archived | 9 | 717 | 726 |
| 合计 | 19 | 3,069 | 3,088 |

active 占全部存量 2.1%，占未归档条目 2.8%。这是存量比例，不能解释为历史晋升成功率：pending 年龄不同，旧 active 还可能已归档。9 月创建且当前仍 pending 的有 2,230 条，当前 active 中有 23 条在 9 月创建。

| 当前 active 的状态原因 | 数量 | 含义 |
|---|---:|---|
| `repeated_success` | 50 | 按成功使用计数和置信度自动晋升 |
| `sustained_usefulness` | 11 | 按曝光、至少一次使用、年龄等条件弱晋升 |
| `init:captured` | 4 | 捕获时直接进入 active |

因此，当前 65 条中 **61 条的状态原因是自动晋升，4 条是直接激活**。59 条 distilled 全部属于自动晋升；6 条 captured 中也有 2 条自动晋升。

59 条 distilled 的源日志中，55 条的 `event_source` 为 hook、2 条为 MCP、2 条为 CLI，全部没有显式 `nomination`。这不支持“全靠用户强调保存才有 active”的猜测。但入口不等于真实行为主体：hook 创建的 trace 后续可能由 agent 补写结果；没有 nomination 也不能证明原对话从未要求保存。`state_reason` 是当前原因，不是完整状态变迁账本。

### 2.2 数量之外，更严重的是内容与证据质量

| 观察 | 数值 | 能说明什么 |
|---|---:|---|
| active 中启发式兜底产物 | 31/65，47.7% | 大量成熟条目走过复制摘要的降级路径；不等于其中每条都无价值 |
| active 中 LLM 蒸馏产物 | 28/65，43.1% | 通用提炼确实存在，但需要继续检查可执行性和信息增益 |
| pending 从未被选中 | 1,608/2,297，70.0% | 大多数候选还没有获得检验机会 |
| pending 从未被标记使用 | 2,170/2,297，94.5% | 产出远多于有反馈的实践；未使用不等于已被证伪 |
| 弱晋升 active 当前只有一次成功记录 | 9/11 | active 不保证至少两次成功实践 |
| 保留日志中的明确任务结果 | 768 次 ok，0 次 fail | 无法据此衡量失败纠错能力；不能理解为实际从未失败 |
| active 对应成功事实 | 513 条，其中 112 条为 inferred | 推断使用也参与成功计数；并不都是明确验证 |
| 上述成功事实缺少输出及摘要 | 313/513 | 历史压缩后，很多“为什么成功”的依据已无法重建 |
| active 当前置信度低于 0.60 | 30/65 | active 是历史状态标签，不代表持续满足晋升线 |

库中另有 44 条 down、362 条 up 反馈，所以不是完全没有负面信号。问题是任务失败这一条反馈通路在保留数据里没有实际样本。

下面仅摘取足以定位问题的内容，短 ID 可在本机检索；不是对全部 65 条做完质量评级后的比例报告。

|---|---|---|
| `9977945a` | 首页统计从“3 Product lines”改成“5+ 厂区”，同步翻译并发布 | 凭两次 inferred 成功记录晋升；一次内容修改的完成事实变成了成熟知识 |

| `0b2b4b3f` | 某项目 agent 运营设计已写好，等待决策后开工 | 后续两条相关任务反馈使它晋升，仍是一条阶段性交接说明 |

应准确表述为：**库里有通用知识，但项目流水账、混合经验包和宽泛格言占用了同一套候选与成熟标签，成熟知识的纯度无法保证。** 不能仅按是否出现项目名、是否用英文，自动判定通用价值。

## 3. 机制上的根因

### 3.1 兜底把“采集不丢失”实现成了“知识必须产出”

`core/src/refine.rs:161` 的启发式实现优先取 nomination，否则取 output_summary，通常直接作为 content。过滤依赖少数“未做代码改动”短语，无法识别大部分发布总结、交接、业务统计。LLM 重试耗尽后的 `ResilientDistiller` 会进入这一路径。

这保障了可用性，却把未提炼材料送入正式知识候选，再接受同一套晋升规则。正确的降级语义应当是：**材料可靠入库，知识提炼可延迟，不能伪装成完成了提炼。**

### 3.2 “成功使用”没有验证规则本身

`core/src/kb/curate.rs:27` 的聚合主要判断存在 used，且同 trace 有 task_ok 或日志 outcome=ok；没有要求逐条规则的结果证据，也没有排除 inferred。

`core/src/kb/curate.rs:488` 的强晋升要求成功次数、成功 trace 数及 confidence 达标。现场参数为 2、2、0.60；两个计数实际来自同一份按 trace 去重的聚合，并不是两种独立证据。v0.1.9 文档仍写 3/2/0.60，分析现场必须以实际参数和源码为准。

不同 trace 不保证不同任务，更不保证独立项目或不同条件。引用了知识、任务整体成功，也不保证这条知识改善了结果。现有 EMA 虽然按 attribution 强度调整增量，但成功计数仍把它算作一条成功事实。

### 3.3 弱晋升拿曝光弥补缺失的验证

`core/src/kb/curate.rs:523` 附近的弱通道要求：selected 至少 20、used 至少 1、年龄至少 14 天、confidence 至少 0.55、没有 down。

曝光次数受到召回排序影响；没有负反馈可能只是没人反馈。以此授予成熟状态，会奖励容易被召回的文本，无法证明可迁移性。修复方向是提高有效验证覆盖，而不是用“没被反对”替代验证。

### 3.4 evolve 主要新增文本，没有形成持续修订的规则

`core/src/kb/evolve.rs:272` 按单条日志蒸馏，相关材料局限于本批次内同 context_key 的日志；`core/src/llm.rs:98` 最多附带 4 条相关交互。最终创建新的 pending chunk，保存单个 distilled_from。

当前没有完整的“新案例匹配已有规则 → 增加支持或反例 → 收窄条件或生成新版本”的演化流程。去重处理不能替代这种归纳。现有 parent_id 也不能当作已经具备规则演化谱系的证明。

### 3.5 泛化提示词存在，但输入和验收不足

`core/src/llm.rs:31` 已明确要求通用原则、排除状态报告。再加一句“请通用化”解决不了问题。

另一方面，要求剥离所有文件、函数、变量名容易误删真正决定适用条件的技术信息。Hook 的摘要主要取最后回复前 400 字（`core/src/hook.rs:196`），通常偏向完成汇报，未必含失败尝试、修复动作及验证。材料不足时让模型必须提炼，容易产出“应全面检查、保持一致”之类格言。

已有 `数据回顾与优化计划-v2.md` 的 B1 建议恢复具体标识符以提高命中。应保留技术条件和诊断信号，但不能把“提高对项目原词的命中”当作通用知识质量目标。该草案的运行可靠性修复可以保留，知识方向需要按本目标重审。

### 3.6 检索、学习、成熟度混用了同一分数

pending 的统一 0.60 降权与 active 竞争；难曝光的候选更难得到使用反馈。相反，长摘要包含许多词汇，可能持续获得曝光。

confidence 又混合任务结果、未选用和时间衰减。“此次不相关”“最近没机会用”“规则错误”被压缩进一个数字。它可以用于启发式排序，但不应单独承载知识真伪及成熟度。

## 4. 重构边界与验收需求

本次只为以下六项需求设计，不扩展成通用记忆平台。

| 编号 | 用户需求 | 最小验收 |
|---|---|---|
| R1 | 默认知识库以可迁移经验为主 | 纯项目状态、交接和发布事实不能直接作为通用规则返回 |
| R2 | 从工作中自动形成候选 | 无需逐条让用户说“记住”；有材料可提出候选，无材料允许零产出 |
| R3 | 候选经实践晋升 | 每次晋升可以展开独立验证事实；曝光、引用、整体 ok 不单独构成验证 |
| R4 | 知识会修正、收窄和退出 | 有效反例可阻止晋升、暂停成熟规则，并形成带来源的新版本 |
| R5 | 能回答“它从哪里来、为什么成熟” | 来源、规则版本、支持、反例及每次状态变化可追溯 |
| R6 | 旧库可重建，已有经验不丢 | 先在副本重建；不继承无法证明的成熟资格；有差异报告和回滚点 |

继续使用 Rust Core、SQLite、现有访问入口和后台处理方式即可。当前问题不需要更换向量数据库、引入图数据库或多 agent 学习平台。

## 5. 新的知识形成过程

### 5.1 分清材料、规则与证据

只建立三种核心语义对象，可复用现有表逐步迁移：

1. **经历材料**：某次任务的条件、尝试、观察结果和项目来源。可以很具体；它是规则的证据，不进入默认通用知识召回。未知结果如实保留。
2. **候选规则**：明确的适用条件、建议动作、可观察的预期结果、已知限制，附来源关系。单次经历可以产生假设，但不能凭生成行为成熟。
3. **验证事实**：某条规则的某个版本，在一个可辨识任务中是否被实际执行、观察到什么、支持还是反驳，附可核查依据。

用户明确要求遵守的偏好、约束和安装技能可以直接生效，但显示为“用户指定/外部提供”，不计入“经验验证成熟”。用户批准保留一条内容，与证明内容正确是两件事。

### 5.2 内容质量门：换个项目后能不能采取同一动作

每条候选至少回答：

- 什么信号出现时应该考虑它？
- 它建议做什么不同的动作？
- 怎么观察这个动作是否有效？
- 哪些条件已知不适用？没有证据的边界标未知，不补写猜测。

保留 SQLite、`BEGIN IMMEDIATE`、错误码、CSS 属性等决定适用性的技术词。移走某次提交 SHA、业务统计值、项目完成状态。项目文件路径可留在来源材料，除非路径本身是技术契约的一部分。

“通常都应该做检查”不能只因措辞通用就过关。需要保留经验相对于常规做法的增量：容易误判在哪里、什么观察推翻了原判断、怎样验证修复。没有增量可以不产出规则。

质量审核可以由模型辅助；模型只能判断候选是否值得试验，不能给自己授予“实践已验证”。

### 5.3 从单案例候选到成熟规则

建议的生命周期为：

```text
经历材料 → 候选规则 → 经独立实践验证 → 成熟规则
               ↑              │             │
               └──── 反例、收窄条件、修订 ──────┘
                              │
                         无效/被替代 → 归档
```

初版晋升采用可解释门槛，不先发明综合学习分：

- 至少两次生成该规则之后的有效实践验证，来自独立任务；同一会话反复记录、重试、改写摘要不增加独立样本数。
- 来源案例用于提出假设，不同时充当“后来验证了假设”的证据。
- 至少一次验证发生在来源项目以外，或能证明确实换了与规则适用性相关的独立环境。两条措辞不同的 query、两枚 context_key 不算迁移。
- 未解决的有效反例阻止晋升。适用条件未知、来源不明时停留在候选，不能靠年龄自动跨过门槛。
- 两次仅是初版保守门槛，不是正确性的数学保证；成熟记录必须展示已经验证的范围，不能暗示所有环境适用。

这些门槛可能暂时减少 active，符合目标。要增加的是经过验证的通用能力，不是标签数量。

同一项目里的多次成功仍有价值：可提高候选在对应条件下的可信程度，但不冒充跨项目迁移证据。项目身份缺失时如实标未知，不能从 agent 名称或随意的查询哈希推断。

### 5.4 给候选真正的验证机会

召回默认返回匹配当前问题的成熟规则；另保留一个受限的候选试用位置，初版每次至多一条，且必须通过相关性和内容质量门。没有适用候选就留空。

候选明确标注未经充分验证，附建议的验证方式。可以先在测试或本地可逆操作中检验；是否用于实际任务由执行 agent 根据任务要求判断，不为积攒证据强行试用。

项目经历不与通用规则争默认召回位置。只有明确查询过去某项目的经历时才检索材料。这样既保留真实经验，又使默认库承担通用指导职责。

### 5.5 反馈落到“规则—动作—观察”

渐进扩展现有 record 协议，每条反馈关联规则版本、任务身份及来源环境，区分：

| 反馈 | 语义 | 能否推进成熟 |
|---|---|---|
| selected / cited | 看见或引用过 | 否 |
| applied，结果未知 | 确实尝试了动作 | 否 |
| supported，附观察依据 | 实际动作与规则预期一致 | 可计入验证，需检查独立性及证据关联 |
| contradicted，附观察依据 | 在声称适用的条件下不成立 | 阻止晋升或触发复核 |
| irrelevant | 对本次任务不适用 | 调整召回/适用条件，不直接判知识错误 |

“所有测试通过”只有在测试针对规则声称的行为时，才能支持该规则。任务整体成功、进程退出码为零、agent 自己说“有帮助”，都不足以自动成为强证据。LLM 判断可协助关联证据，仍需保留实际观察；没有观察就是 unknown。

Hook 继续自动采集可确认的事实，不能猜 outcome。执行 agent 在正常收尾中补少量结构化结果，不要求用户每次人工审批知识，也不要求用户为每条经验点赞。失败、用户纠正、弃用方法与成功一样进入材料层；只有确实针对规则的反例才用于反驳，避免将无关任务失败误扣给知识。

### 5.6 evolve 的新职责：归纳、补证、修订

后台按新经历或新验证事实触发处理：

1. 提取有信息增量的候选；无足够材料就不产出。
2. 检索已有相关规则，判断是同一机制的新证据、独立的新规则，还是矛盾。相似度只负责找候选，不能直接决定合并。
3. 同一机制补证，不复制成多个近似格言；存在差异则保留条件差异，不能机械合并。
4. 反例出现时，暂停受影响规则的成熟资格，检查是使用越界、规则不成立还是材料有误。
5. 需要改动作、条件或预期时创建新版本，保留旧版本和改变原因。旧证据不能无条件继承，重新判断它是否支持新版本。
6. 仅当证据门槛满足时晋升，并记录本次判断所用事实。

禁止“LLM 不可用 → 复制摘要当知识”的兜底。不可用时材料继续可靠保存，提炼任务保持待处理，暴露延迟和错误；恢复后接着处理。

### 5.7 不再用一条 confidence 同时代表所有事情

展示上先采用状态与可展开证据，不为美观展示伪精确的正确率。

- 相关性决定本次该不该召回。
- 成熟度由有效验证、迁移范围和未解决反例决定。
- 新鲜度只对可能过时的适用条件提出复核需求。
- 时间久、被看见没用上，可以降低曝光优先级或移出活跃候选池，不构成事实上的反证。

首版不需要把这些因素再揉成一个新总分。原有 confidence 可保留作迁移期诊断数据，但不能直接映射为新的成熟资格。

## 6. 一个真正发生“晋升”的例子

以现有库里的布局踩坑为原料，下面是预期过程示例，不代表这些验证已经发生：

1. 项目 A 的页面标题被裁，观察发现某层纵向 flex 中子元素实际高度低于自然高度；修复后截图与尺寸测量恢复。
2. 形成候选：“纵向 flex 容器高度受限时，检查本层子项是否被收缩；对不应缩小的标题区调整 shrink，并让指定内容区承担滚动；用实际尺寸和溢出测量验证。”来源中的项目文件和数值留在案例中。
3. 项目 B 出现相同机制，应用后通过对应布局检验，增加一次迁移验证。
4. 另一个独立任务再次验证，且没有未解决反例，候选成熟。
5. 后续发现裁切实际由祖先 overflow 引起，若不满足规则条件，记录边界；若满足原条件仍失败，阻止继续无条件推荐并修订规则。

这里增长的是规则的依据与适用边界，必要时规则内容也改变。旧系统更多是在给“项目 A 改了若干页面”这段文字累加使用次数。

## 7. 迁移：破坏旧语义，保留原始依据

### 7.1 先在副本重建

保留一致性备份，固定此次快照。将旧库的内容、来源、反馈及状态原因保留为历史，不在原库直接批量删除或重写。

将条目重新评估为：

- 纯项目状态：回到经历材料，不进通用规则召回。
- 含经验的混合总结：拆出候选，与原文建立来源关联。
- 通用但空泛、无操作增量：不进入候选，保留淘汰原因。
- 已有清晰规则：进入候选并核对可用证据。
- 用户明确指定的约束：保持有效且标注来源，单独展示。

来源不能只按 `source=chat/manual` 机械决定，需检查内容及可用出处，无法确认的留待核实。

### 7.2 不把旧 active 批量搬成新成熟规则

现有 513 条成功事实里，313 条已没有输出材料；同时缺少可信的独立任务和项目验证身份。不能为了保住 65 这个数字补造证据。

能追溯的事实逐条重评；剩下的作为“历史报告曾有用”，不计入新的独立验证门槛。旧规则因此回到候选，不代表把经验删除。

保留支撑规则的紧凑证据：条件、动作、观察、来源引用及摘要。原始完整会话可以继续按保留策略压缩，但不能连规则为何成立的唯一证据一起清掉。

### 7.3 分三步交付

| 阶段 | 具体产物 | 完成条件 |
|---|---|---|
| 1：分离材料与知识入口 | 新数据语义、提炼质量门、LLM 故障只保存材料；取消新学习路径的弱晋升 | 发布汇报、交接、模型失败均不能直接制造成熟规则；偏好可正常生效 |
| 2：建立验证晋升闭环 | 规则版本反馈、独立任务验证、候选试用、反例修订、晋升记录 | 从自动发现到实践验证再到晋升可端到端跑通，重复记录不能刷成熟度 |
| 3：重建旧库并对比 | 迁移副本、逐条处置表、留出任务评估与迁移差异报告 | 核查默认召回质量、证据完整性及回滚恢复后，再切换正式库 |

破坏性变更应使用显式版本迁移。MCP、CLI、Web、SDK 同步解释新成熟度；旧 API 的 `outcome=ok + used` 兼容为旧式使用报告，不能偷偷升级为新强验证。`approve` 应表示用户保留/指定，不能再与自动验证成熟混为一谈。

## 8. 用什么证明这次重构有效

不要把 pending/active 比、蒸馏产量、曝光次数当成主 KPI。主要看：

- 默认召回中可执行、可迁移规则的比例，以及一次性项目状态污染率。
- 候选得到有效验证的覆盖率；严格区分没机会用、尝试无结果和验证失败。
- 成熟规则中具有可追溯独立实践及迁移证据的比例。
- 同类错误再次发生率、用户重复纠正同一问题的频率。
- 反例出现后，错误规则被暂停、收窄或修订的情况。
- 相对于不注入知识，同一类留出任务的表现是否改善；成本用每条有效规则或有效验证衡量。

离线评估按任务/项目分组留出：不能用某段经历提炼出规则后，又把同一经历改写成问题来证明有效。历史回放只能评估候选质量和可能帮助，不能补造实际使用事实。跨项目收益最终仍需未来任务验证。

必须通过的行为验收用例：

| 场景 | 预期 |
|---|---|
| “某次发布完成，测试通过，已推送” | 保存经历，零条直接成熟知识 |
| 同一案例反复提交、十个 trace 转述同一结果 | 仍是同一验证单位，不能晋升 |
| selected 100 次，cited 多次，没有动作与结果证据 | 不能晋升 |
| 规则出现前的来源案例 | 可支持提出假设，不冒充生成后的验证 |
| 两次独立实践含来源之外迁移，材料可核查 | 满足初版成熟门槛；晋升时展示证据 |
| 总体任务成功，但规则对应检查失败 | 记录该规则反例，不授予成功验证 |
| 有反例但模型称“高度可信” | 仍不能晋升；模型信心不覆盖观察 |
| 修改了规则动作或适用条件 | 产生新版本，旧成功次数不自动全量继承 |
| LLM 不可用 | 材料保存、提炼延迟，无摘要冒充知识 |
| 旧 active 缺少支撑材料 | 保留历史与候选资格，不能自动成为新成熟规则 |

## 9. 证据边界与复核方式

本报告不将“没有记录失败”解释成“从未失败”；不将 provider、source 或 state_reason 当作完整的人类意图证明；不声称已精确测出通用知识占比。当前库可以支持诊断方向，不能补足已压缩掉的因果依据。

现场使用只读连接制作 SQLite 一致性快照，再对副本查询。任务开始的常规 recall 会产生自己的 trace，但没有修改现有知识条目的内容或状态，也没有运行治理或迁移。本报告仅提出设计。

核心统计可用以下只读 SQL 复核，持续运行的正式库数字可能继续变化：

```sql
SELECT state, origin, COUNT(*) FROM chunks GROUP BY state, origin;

SELECT state_reason, COUNT(*) FROM chunks
WHERE state = 'active' GROUP BY state_reason;

SELECT distill_provider, state, COUNT(*) FROM chunks
WHERE origin = 'distilled' GROUP BY distill_provider, state;

SELECT COUNT(*) AS pending,
       SUM(selected_count = 0) AS never_selected,
       SUM(used_count = 0) AS never_used
FROM chunks WHERE state = 'pending';

SELECT outcome, COUNT(*) FROM episodic_log GROUP BY outcome;

SELECT COUNT(*) AS success_facts,
       SUM(e.output IS NULL AND e.output_summary IS NULL) AS missing_material
FROM chunk_success_traces s
JOIN chunks c ON c.id = s.chunk_id
LEFT JOIN episodic_log e ON e.trace_id = s.trace_id
WHERE c.state = 'active';
```

**设计取舍：允许材料丰富、候选谨慎、成熟知识稀少；要求每一条成熟知识能解释自己为何值得复用，并能被新的实践改变。**
