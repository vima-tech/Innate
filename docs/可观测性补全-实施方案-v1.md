## 1. 背景与动机

`KnowledgeBase::inspect()`(`core/src/kb/inspection.rs`)当前已输出 30 天窗口内的:
trace 闭环率、usage annotation 率、selected→used 率、task success 率、feedback coverage、
distill cost、knowledge debt ratio、intuition calibration、confidence 分布、suggestions。

即时(point-in-time)可观测性**不弱**,但有三类盲区在真实运维中已造成代价:

1. **daemon 健康完全不在 `inspect` 里**。`daemon_errors` 存在独立的
   `~/.innate/data/daemon_state.sqlite`,只以 `innate daemon status` 的扁平 `count(*)`
   出现,不分 operation。一个 daemon 在原地升级二进制后跑在已删除 inode 上、每次
   shell-out 都失败的 bug,因此被一个扁平累计数(4273)埋了约两周才被发现。
2. **LLM/Embedding 调用健康不可见**。`~/.innate/logs/llm_trace.log` 只有原始 JSONL
   明细,从未聚合成成功率/延迟/错误码分布。embedding provider 账户欠费
   (HTTP 400 Arrearage)在任何指标里都看不到。
3. **零时序基础设施**。一切都是即时快照,无法回答"债务比/产出率/错误率在变好还是变坏"。

此外还有四个"只能靠手查 SQL"的缺口:
- 召回质量为什么变好/变差(候选?排序?预算?spread 噪声?)。
- 具体哪个 source / agent / context 在变差。
- recall/record/evolve/distill 的延迟、失败、排队、成本不可见。
- 离线 `recall-eval` 与线上反馈指标缺统一视图。

## 2. 设计原则(对齐 `AGENTS.md` 架构约束)

- **确定性、无 LLM、读路径优先**:所有指标从既有表/日志聚合,不引入新依赖,可在热路径外随时算。
- **复用既有底座**:`inspect()` 为主聚合点;`llm_trace.rs` / 新 `operation_runs` 表做运行级摘要;daemon 健康用**独立只读连接**读 `daemon_state.sqlite`(非 ATTACH,见 §5.1)。
- **单二进制 + 薄封装**:核心逻辑在 lib,CLI / MCP / Web 仅转发(`inspect()` 复用,新增端点薄封装)。
- **分层归类**:即时派生指标 → 召回解释 → 运行指标 → 展示/eval,四层递进。
- **防膨胀**:`recall_snapshot` 只存聚合 + 少量 top 异常;`operation_runs` 不存 prompt/response,且配 retention 清理。
- **先诊断后趋势**:第一阶段优先回答"哪里坏了、为什么坏";趋势快照只记录稳定 KPI,避免早期把半成品指标固化成长期契约。

## 4. 三个错误存储的边界模型(关键,避免重复计数)

合并后系统有三处记录运行/错误信息,**职责必须互斥**:

| 存储 | 职责 | 写入时机 | 去向 |
|---|---|---|---|
| `llm_trace.log`(JSONL) | LLM/embed **原始**请求响应明细(预览、延迟、重试、错误;永不含 API key) | 每次 HTTP 调用 | Web 明细页 `/api/llm-traces` |
| `operation_runs`(新 DB 表) | **进程内**每次操作摘要(status/duration_ms/error_kind/counts) | recall/appraise/record/evolve/curate/distill/embed 入口 | `inspect.operational` 延迟/吞吐/错误聚合 |
| `daemon_errors`(daemon_state.sqlite) | daemon **监督级 / shell-out** 失败(子进程 spawn 前、调度层) | daemon watch loop | `inspect.operational.daemon` |

**为什么三者都要**:daemon 以子进程 shell-out 跑 recall/evolve,deleted-exe 这类失败发生在
**子进程启动之前**,根本不会写 `operation_runs`——所以 daemon 健康必须独立采自
`daemon_errors`,不能被 `operation_runs` 替代。
KPI 错误率按 op 类别指定**单一权威源**,不跨存储重复计。

`metric_snapshots`(状态型 KPI 每日 rollup)与 `operation_runs`(操作事件流)**互补不重叠**:
debt_ratio、pending 最老年龄、confidence 分布是**状态比值,无法从事件流重建**,故需独立快照表。

**迁移编号**(对照 `migrate.rs` 的单步 `MIGRATIONS` 数组、文件在 `core/src/migrations/`,**同名文件只能有一个**):
- **4.18→4.19** = 仅 `ts` 索引(随 P0/P1 发布,无新表、纯加索引)。
- **4.19→4.20** = `operation_runs`(随 P3a 发布)。
- **4.20→4.21** = `metric_snapshots`(随 P3b 发布)。
分三个独立、幂等、只加不删的迁移,**杜绝同名迁移冲突与长期空表**;每个迁移对应一次 schema_version 步进,符合既有增量迁移哲学。

每次 schema bump 必须同步**五处**(漏一处即漂移):
1. 新增 `core/src/migrations/<from>_to_<to>.sql`;
2. `migrate.rs::MIGRATIONS` 数组追加该步;
3. `migrate.rs::TARGET` 改为新版本号;
4. `storage/mod.rs::EXPECTED_SCHEMA_VERSION` 改为新版本号(**易漏的运行期闸门**);
5. `schema.sql` 新建库 DDL + 设计文档 schema 版本说明。

## 5. 指标目录

### 5.0 术语定义(实现前先统一,避免各自解读)

| 术语 | 操作化定义 |
|---|---|
| **empty recall(空召回)** | `RecallResult.empty == true`,即 knowledge 与 sparks 都为空;落库侧表现为 `episodic_log.usage_state='known_none'` 且 `distill_state='discarded'`。不要只看 knowledge,否则 include_sparks 命中会被误判为空 |
| **zombie chunk(僵尸 chunk)** | 非 archived 且 `selected_count >= recall.repeat_select_min 且 used_count = 0` 的 chunk——即一直被召回进上下文却从不被采用、白占预算者。与 curate 的 `repeated_selected_unused` 归档条件同源,但 zombie 统计**不要求** `confidence < repeat_select_conf_max`,故能暴露"逃过归档"的高置信僵尸 |
| **state_transition_approx(状态转移近似)** | 当前 schema 只有 chunk 当前 `state/state_reason/state_updated_at`,没有历史状态事件表;窗口内只能按 `state_updated_at >= cutoff AND state_reason IN (...)` 近似统计 promotion/eviction,不能声称是严格 rate |
| **promotion rate(精确晋升率)** | 需要状态转移事实表或 operation_runs 记录 curate/approve 的转移计数后才能准确计算;P1 不输出精确 rate |
| **eviction rate(精确淘汰率)** | 同上;P1 只输出 archive/promotion 近似计数与 backlog age |
| **agent_coverage** | 见 §5.1 —— **必须分通道**,不可全局一刀切 |
| **错误率(errors_24h/7d)** | 对应错误存储中 `ts > now - 窗口` 的行数,**非累计 count**(累计数曾把 deleted-exe bug 埋两周) |

### 5.1 即时派生(P1,纯 SQL,不新增业务表)

**多窗口**:所有率指标输出 `1d / 7d / 30d` 三档(当前仅 30d)。

**按维度分解**(`event_source` / `agent` / `context_key`):
- recall 数、empty recall 率
- completed 率、timeout 率
- usage annotation 率
- selected→used 率
- task success 率
- feedback coverage
- **agent 归因覆盖率**(非 NULL %)——**必须分通道算**,见下方陷阱

> **⚠ agent_coverage 结构性 NULL 陷阱**(必读):按 `AGENTS.md`,**hook/Stop 与 daemon 捕获通道当前不注入 `INNATE_AGENT`,这些行的 `agent` 按设计就是 NULL**。因此**全局** agent_coverage 永远 < 100%,若据此触发 suggestion 会**常驻误报**。
> 正确做法:agent_coverage 按 `event_source` 分通道输出;**suggestion 只在"应当有 agent 的通道(`event_source IN ('mcp','cli')`)出现意外 NULL"时触发**——那才是真实配置缺失信号(正是本会话发现的 `~/.claude.json` 缺 `env.INNATE_AGENT`)。hook/daemon 的 NULL 视为预期,不计入告警。

实现注意:`context_key` 分解以 `episodic_log` 为锚点;涉及 chunk 级事件时按
`usage_trace.trace_id = episodic_log.trace_id` join,不得假设 `usage_trace` 有 context 列。

多窗口计算建议:用**单次窗口扫描 + 条件聚合**(`SUM(CASE WHEN ts > cutoff_1d THEN 1 END)` …)在一遍内同时产出 1d/7d/30d,避免对同一表跑三遍;依赖 §6 P0 的 `ts` 索引。

**召回包质量**:
- 平均 retrieved 数、selected 数
- selected rank 分布
- selected-but-never-used top chunks
- high-rank-unused / low-rank-used 异常样本
- empty recall 率优先用 `episodic_log.usage_state='known_none'`;旧数据若没有该状态,再 fallback 解析 `recall_snapshot.selected=[] AND sparks=[]`。

**知识生命周期**:
- pending 最老年龄
- `state_transition_approx`:窗口内 `state_updated_at` 命中的 `approved/repeated_success/restore` 与 `low_confidence/repeated_selected_unused/never_used/invalidated/archive reason` 近似计数
- zombie chunk 数与比例
- governance proposal backlog age
- 精确 pending→active 晋升率、active→archived 淘汰率不在 P1 承诺;P3 后从 operation_runs counts 或新增状态事件再算。

**evolve/distill backlog**:
- pending evolve 最老等待时间
- failed evolve / failed distill 按错误窗口统计
- screening stuck age 分布

**运维健康**(并入 `operational`,补对方方案盲区):
- daemon `errors_by_operation` + `last_error` + `errors_24h` / `errors_7d`(**错误率而非累计数**)
- daemon liveness:running / pid / last_event_ts / 读取 lag(offset vs 文件大小)

实现建议:新增 `daemon::health` 只读 helper,由 `inspect()` 调用;路径只通过 `paths.rs`。
**用独立的 `Connection::open_with_flags(…, SQLITE_OPEN_READ_ONLY)` 打开 `daemon_state.sqlite`,不要 ATTACH 进主连接**——ATTACH 会把 daemon 库的锁/损坏耦合进主 `inspect` 事务;独立连接里任何失败(不存在/损坏/被锁)都能 catch 后降级,主库指标不受影响(这也与既有 `daemon status` 单独开连接的做法一致)。`daemon_state.sqlite` 不存在时返回 `{ "state": "never_run" }`,损坏/被锁时返回 `{ "state": "unknown", "error": "…" }`,均不得让 `inspect()` 失败。

### 5.2 召回解释 — `recall_snapshot` schema 2(P2)

向后兼容地把 snapshot 升级为带版本结构(旧 snapshot 仍可解析):

```json
{
  "schema": 2,
  "retrieved": [],
  "selected": [],
  "sparks": [],
  "skipped_reasons": {},
  "session_only": false,
  "recall": {
    "budget": 6000,
    "top": 10,
    "expand_deps": "false",
    "rerank": false,
    "channels": { "content": 12, "trigger": 8, "lexical": 3, "spread": 0 },
    "scores": { "max": 0.82, "min_selected": 0.51, "avg_selected": 0.63 },
    "packing": { "selected_tokens": 2100, "skipped_by_budget": 4, "skipped_by_dep_depth": 1 }
  }
}
```

可回答:lexical 降还是 vector 降?ACT-R spread 是否拉进无效候选?预算太小跳过好 chunk?
rerank 改了排序却没提高 used rate?
**只存聚合 + 少量 top 异常,不塞 per-candidate 明细,防日志膨胀。**

实现可行性(已核实,P2 不需新增候选追踪):
- `channels` 计数直接由 `ann_candidates` 产出的每候选 `CandidateInfo.sim_{content,trigger,lexical,spread}` 是否 `> 0` 统计得出——通道来源已逐候选记录。
- `packing.skipped_by_dep_depth` 复用已有的 `dep_depth_limit` skip 原因,它已经写入 `skipped_reasons`。
- `packing.skipped_by_budget` **不能**从现有 `skipped_reasons` 得出:当前 `pack()` 预算超限只把 block 推入 `skipped` 临时列表,不落 reason。P2 需要新增一个局部聚合计数(例如 `budget_skipped_count = skipped.len()` 或更细分 `budget_skipped_tokens`)并写入 snapshot。
- `scores.*` 取 selected 集合的 fused_score 聚合,recall 打包时已在手,无需重算。

### 5.3 运行指标 — `operation_runs` 表(P3a,schema 4.19→4.20)

```sql
CREATE TABLE IF NOT EXISTS operation_runs (
  id          TEXT PRIMARY KEY,
  trace_id    TEXT,
  op          TEXT NOT NULL,       -- recall/appraise/record/evolve/curate/distill/embed/hook_recall
  source      TEXT,
  agent       TEXT,
  status      TEXT NOT NULL,       -- ok/error/timeout
  error_kind  TEXT,
  started_at  TEXT NOT NULL,
  duration_ms INTEGER NOT NULL,
  counts_json TEXT,
  params_json TEXT
);
CREATE INDEX IF NOT EXISTS idx_opruns_op  ON operation_runs(op);
CREATE INDEX IF NOT EXISTS idx_opruns_ts  ON operation_runs(started_at);
CREATE INDEX IF NOT EXISTS idx_opruns_tid ON operation_runs(trace_id);
```

派生:`recall_p50/p95_ms`、`embedding_p95_ms`、`evolve_duration_ms`、`distill_success_rate`、
`error_kind` top list、按 source/agent/context 分解性能。

**约束**:
- **失败路径也必须写**(status=error/timeout + error_kind),否则失败不可见。
- **配 retention**:curate 按新 meta `metrics.retain_days`(默认 30)清理旧行,防无界增长拖慢 COUNT(参照 `purge_usage_trace`)。
- raw LLM 内容仍只在 `llm_trace.log`,本表只放摘要。
- embed/distill 也写本表 → **吸收"LLM 健康聚合",`llm_trace.log` 退回纯明细**(比聚合 JSONL 更干净)。
- 打点用 RAII/闭包式 helper 收口,避免每个入口手写 start/end 导致失败路径漏记。
- context 维度不进 `operation_runs` 列;按 `trace_id` join `episodic_log.context_key` 统计,避免字段重复和不一致。
- **`embed` op 两阶段打点**:
  - P3a 第一版在高价值 call-site 包一层:recall 的 `embed_both`、add/spark/promote/distill 写 chunk 前的 embedding、rebuild_embeddings。这样不把 `Storage`/DB 连接塞进 `EmbeddingProvider`,实现风险低。
  - 若重复代码明显,再评估 `MeasuredEmbeddingProvider` decorator。该 decorator 不能复用主 `Storage` 可变事务句柄;最多持有独立 metrics writer/连接,并必须避免在外层 `BEGIN IMMEDIATE` 内再抢写锁。
  - `LlmEmbeddingProvider` 同时已写 `llm_trace.log`——二者不冲突:llm_trace 是原始明细,operation_runs 是聚合摘要(见 §4 边界模型),但**统计"embedding 健康"以 operation_runs 为准**,避免两套口径。

### 5.3.1 error_kind 受控词表(必须先定义,否则无法聚合)

`error_kind` 是 `operation_runs` 与 daemon 健康聚合的**分组键**。若各入口自由填字符串,"error_kind top list" 会碎成几十种近义值,失去价值。统一在 `storage/metrics.rs` 提供
`classify_error(&InnateError) -> &'static str` + `classify_message(&str) -> &'static str`
(daemon/HTTP wrapper 使用 message 分类),取值**封闭**:

| error_kind | 来源 | 备注 / 为何单列 |
|---|---|---|
| `embedding_arrearage` | `EmbeddingUnavailable` 且 message 含 `Arrearage`/欠费 | **单列**:这是账单问题、可直接处置,正是本会话被埋住的失败 |
| `embedding_unavailable` | `InnateError::EmbeddingUnavailable`(其余) | 嵌入服务不可用/超时/解析失败的通用桶 |
| `llm_http_error` | distill/rerank 的 HTTP 非 2xx | 与 embedding 区分,定位是生成侧还是嵌入侧 |
| `llm_timeout` | LLM/embed 调用超时或 message 含 timeout/deadline | status=`timeout` 配套 |
| `db_locked` | `rusqlite::Error` 且为 `SQLITE_BUSY`/locked | 锁竞争单列,指导是否调 busy_timeout |
| `db_error` | 其余 `InnateError::Db` | |
| `json_parse` | `InnateError::Json` | |
| `chunk_not_found` | `InnateError::ChunkNotFound` | |
| `invalid_state` | `InnateError::InvalidState` | 含向量维度守卫 fail-closed、lease 冲突 |
| `io_error` | `InnateError::Io` | |
| `spawn_failed` | **仅 daemon 侧**:子进程启动失败(`No such file`/`ETXTBSY`) | deleted-exe 类;operation_runs 永远看不到(spawn 前就失败),只在 `daemon_errors` |
| `timeout` | 操作级超时(非 LLM) | |
| `other` | `InnateError::Other` 兜底 | 兜底桶应保持小;若某类 `other` 变多,反推它该单列 |

规则:**新增失败类型时先扩这张表再用**,禁止在调用点即兴拼 error_kind 字符串。

### 5.4 状态快照 — `metric_snapshots` 表(P3b,独立 4.20→4.21 迁移)

### 5.5 召回质量代理(P1 已含部分,P4 补 eval 对接)
- used chunk 命中 rank(MRR 代理)、零结果召回率、selected-未-used 率。
- 与 §5.1 去重:empty recall 率、selected-未-used 率已在 §5.1 产出,本节只额外补 used-rank(MRR),不重复定义。
- `hook_silence_rate` 只能做近似:当前 `innate hook prompt/session-start` 在 query 非空时会执行 `recall(trace=true,min_score=...)`,低分候选被过滤后可落 `event_source='hook' AND usage_state='known_none'`;但 query 为空或 hook 吞错时主库没有 attempt 行。因此 P1/P4 若展示该指标,命名必须是 `hook_known_none_rate`;精确 silence rate 需 P3a 在 `operation_runs(op='hook_recall')` 或单独 `hook_attempts` 中记录每次 hook attempt。

### 5.6 `inspect()` 输出契约骨架(定顶层形状,防膨胀 + 对接 SDK 类型)

新指标**一律**挂到下列新顶层键下,**绝不改名/移动既有键**(`chunks`/`feedback_loop`/`intuition_calibration`/`params`/`suggestions` 等保持原样),以免破坏现有 SDK 与 Web:

```jsonc
{
  // …既有字段原样保留…
  "observability": {                    // P1,纯派生
    "windows": { "1d": {…}, "7d": {…}, "30d": {…} },   // 各窗口的率指标
    "by_dimension": { "event_source": {…}, "agent": {…}, "context_key": {…} },
    "recall_pack": { "avg_retrieved": …, "avg_selected": …, "zombie_chunks": …, "selected_unused_top": [...] },
    "lifecycle": { "pending_oldest_age_days": …, "state_transition_approx": {…}, "backlog": {…} }
  },
  "operational": {                      // P1 daemon + P3a ops
    "daemon": { "state": "running|stopped|never_run", "errors_by_operation": {…},

             "error_kind_top": [...] }   // P3a 起,来自 operation_runs;无表时省略该子块
  },
  "trends": { … }                       // P3b 起,来自 metric_snapshots;无数据时省略
}
```

约束:`operational.ops` 与 `trends` 在对应表/数据不存在时**整块省略**(而非填空对象),让 SDK 类型用 optional 表达分期可用性。`InspectResult`(TS)按此骨架加 optional 字段。

## 8. 风险与待决

- **operation_runs 热路径写成本**:recall 本就已写 usage_trace + episodic_log 多行,多一条轻量 insert 属增量;但仍按 P3a 分批插桩,先覆盖非最高频路径,再用基准决定 recall/record 上线时机。
- **指标 JSON 契约膨胀**:`inspect()` 输出会变大。按 §5.6 骨架统一挂 `observability` / `operational` / `trends`,旧字段不改名不移动;分期未就绪的子块**整块省略**,SDK 用 optional 字段表达。
- **跨库 daemon health 锁竞争**:daemon 状态只读打开,失败降级为 health error,不得影响主 `inspect()`。
- **精确生命周期 rate 缺事实表**:当前 chunks 只保留最后状态,不能重建窗口起始分母与多次转移。P1 只能给近似计数;精确 rate 要么从 P3 operation_runs counts 落地,要么新增状态转移事实表。
- **待决项**:是否在 P4 引入 `/api/metrics/trend`。默认先复用 `/api/inspect`;只有 Web 图表需要更长窗口时再加端点。

## 附:与"另一份 LLM 方案"的差异(本方案做了哪些修正)

1. **不砍 daemon 健康**——对方四层未触及 daemon,而 daemon 监督级失败正是本会话被埋两周的盲区;operation_runs 无法覆盖子进程 spawn 前失败。
2. **operation_runs 必配 retention**——对方未提,否则无界增长。
3. **LLM 健康折进 operation_runs** 而非聚合 JSONL——采纳对方更干净的做法,`llm_trace.log` 退回纯明细。
其余以对方方案为骨架(多窗口 + 维度分解 + recall_snapshot 解释层 + Web/eval),本方案与之一致。
