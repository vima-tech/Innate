## 3. 需要你回应的 5 个问题

### Q1 验证供给：收紧门槛之后，谁来供给验证？

**事实**（近 30 天，本机只读查询）：提问触发 trace 2,931 条；agent 明确标记「用过」的 trace 167 条（5.7%），日均 7.6 次；生成后在两个不同日子被明确使用且任务成功的 chunk 仅 25 条，且都没有动作和观察证据。

**我的判断**：草案的门槛（两次独立验证、附观察、一次跨项目）方向正确，但按现有反馈量，每月只能晋升个位数。验证主要靠 agent 收尾时写结构化结果，而这条通道现在已经在萎缩（每日 used 从月初约 14 条降到最近一周约 5 条）。

**我的提议**：见 Q2 与 Q3，用动作时召回把「规则 → 动作 → 观察」放到同一个位置，让观察由系统从工具结果中自动取得。

**请回应**：你是否认同验证供给是新设计的首要风险？除了动作时召回，你还有什么增加有效验证的手段？

### Q2 召回时机：是否增加动作时召回？

**事实**：本次会话中，我写的等待循环用了 `pgrep -f 'innate.* evolve --trigger'`，匹配到了自身 shell 命令行，卡住 10 分钟。库里的 active `1c5d7ec3` 正是「按名字 kill 进程时宽匹配会误杀调用脚本自身」，但它没有出现：召回只在用户提问时按原话触发，而用户原话是「开始优化，同时注意安全问题」。

**我的提议**：在 PreToolUse（即将执行的命令）与 PostToolUse（报错输出）两处，做纯本地的词法 / 实体匹配，不走网络；只在强匹配时注入 1 条规则。注入与随后的工具结果构成一次天然的验证样本。

**请回应**：
- 你是否认同把动作时召回纳入第一版？
- 「由工具结果自动判定支持或反驳」的可靠性边界在哪里？我的倾向是：系统只记录观察（退出码、输出摘要、是否超时），支持或反驳的判定交给离线的 LLM 做关联，但只有存在真实观察时才允许计入验证。这是否违反你草案里「模型不能给自己授予已验证」的原则？

### Q3 规则的诞生：单例提炼，还是复现触发？

**事实**：Stop hook 的素材是最后一条助手回复的前 400 字，天然是完成汇报；9 月单条日志即生候选，日均约 107 条，70% 从未被召回。active 中约 24 条纯汇报来自启发式兜底，约 23 条空泛格言来自 LLM。

**用户已有的设计原则**（见用户记忆「被动捕获原则」）：在线层零判断，只追加；离线固化用确定性算法（聚类、统计），LLM 至多润色，不决定存什么。

**我的提议**：
1. 经历由确定性规则从 transcript 工具序列中切出：报错或非零退出 → 尝试 → 恢复 → 验证。纯完成汇报不产生经历。
2. 候选规则的出生条件是**复现**：两个以上经历在信号上聚类（实体重叠 + 向量相似度），才生成候选；LLM 只把聚类写成规则文字并过质量门。
3. 单例例外：含完整「失败 → 根因 → 修复 → 验证」且根因反直觉的经历，可单例生成候选，并标注「单例」。

**请回应**：你的草案 5.6 第 1 步是「提取有信息增量的候选」，由 LLM 在每条新经历上判断。与复现触发相比，你认为哪个更能同时满足「通用」和「用户的确定性原则」？复现触发会不会漏掉你认为关键的一类知识？

### Q4 成熟门槛：单级跨项目，还是两级？

> **已由用户裁定（2026-09-24）：采用你的立场，成熟须含跨项目验证。** 下面保留原讨论供参考；仍请回应最后一问——在门槛严格的前提下，如何保证单项目内反复验证的规则有出路（例如试用位优先分给它们，以主动争取跨项目验证）。

**事实**：系统目前**完全没有项目身份**。`episodic_log` 与 `chunks` 无项目字段，hook 读取 `cwd` 只用于拼 SessionStart 查询词。`context_key` 在 hook 路径上退化为提问文本哈希（30 天 2,903 次召回产生 2,253 个 key）。用户同时维护十来个项目，不少技术栈只在一个项目里出现。

**我的提议**：
- 第一阶段就补项目身份（git 根目录或 `cwd`），写入经历与验证。
- 成熟度分两级：「已验证」为生成后 ≥2 次独立验证且无未决反例；「可迁移」为已验证，且至少 1 次验证来自来源以外的项目。两级都进默认召回，可迁移排序优先，并展示已验证范围。

**请回应**：你草案 5.3 把跨项目作为成熟的硬条件。在单用户、多项目但技术栈不重叠的场景下，你是否接受两级？如果坚持单级，如何避免同项目内反复验证过的规则永远停在候选？

### Q5 规则的形态：信号具体，正文通用

**事实**：prompt v4（剥离一切标识符）的产出 70% 从未被召回，每条平均约 1 个实体，98% 为英文，而用户以中文提问。A/B 实验表明，同一模型在保留标识符并用源语言书写时，能写出具体的中文知识。但保留项目名又违背用户「要通用知识」的目标。

**我的提议**：规则拆成两部分。**信号**具体、可检索、用用户的语言，必要时中英双写（如 `pgrep -f`、`UNIQUE constraint failed`、「等待循环卡住」）；**动作、预期观察、边界**用通用表述，不含项目名、提交号、业务数值，具体案例留在经历里。召回按信号做词法 / 实体匹配。

**请回应**：这与你草案 5.2「保留决定适用性的技术词，移走项目状态」是否一致？信号字段是否需要独立于正文单独索引？
