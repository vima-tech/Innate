## 0. 一句话结论

飞轮的**产能端是好的**（459 条 pending 内容质量不差），但**闭环端几乎断了**：13,576 次召回选择只换回 381 次 `used`（2.8%），而承担 98.5% 召回量的 hook 通道贡献 **0 条**反馈；与此同时后台每 60 秒空转一次全量 curate，30 天烧掉约 22 CPU 小时。优先级应当是「先修闭环与空转，再谈召回精度」。

## 2. 问题清单（按严重度）

### P0-1 后台每 60 秒空转一次全量 curate
**证据**：`daemon/watch.rs:40` `EVOLVE_POLL_INTERVAL = 60s`；`kb/evolve.rs:48-57` 在 `trigger=="scheduled"` 且无 evolve_request 时**仍然执行 `curator.run()` 全量 curate** 后才返回。30 天 evolve/curate 各 39,383 次 ≈ 22 CPU 小时，而同期 distilled 产出仅 414 条。
另：`watch.rs:227` 的 `manual` evolve 成功后，`watch.rs:246` 又补一次 `scheduled` evolve——日志里成对出现的 "end evolve ok" 即此。

**影响**：常驻 CPU 与磁盘 IO 浪费；每次都要开库并把 719×2 条向量载入内存。

### P0-2 hook 通道零反馈，47.5% 的 trace 直接超时
**证据**：hook 产生 13,386 次 `selected`（98.5%），`used`/`task_ok` **一条都没有**；5,639 条 hook episodic_log 里 2,679 条 `timed_out`、1,903 条停在 `recalled+known_none`，只有 238 条（4.2%）走到 `completed+known_some`。所有反馈都来自 agent 事后主动调 MCP `innate_record`。

**影响**：置信度 EMA、`promote_used_success_min` 晋级、`repeat_select` 淘汰全部依赖 `used`，输入端断供 → 治理闸门（P1-6）必然堵死。

### P0-3 record 被整体拒绝，MCP record 失败率 16%
**证据**：`operation_runs` op=record source=mcp → ok 281 / **error 54，error_kind=invalid_state**。根因在 `kb/record/evidence.rs:4` `validate_trace_attribution`：`used` 列表里只要出现一个不在该 trace `selected` 集合中的 id，**整次 record 失败**，agent 已正确应用的其余 chunk 也一并丢失。

**影响**：把本就稀缺的反馈又砍掉 16%。

### P0-4 LLM 蒸馏链路半死，且 inspect 完全看不出来
**证据**：`llm_trace` 累计 351 次 chat，**73 次失败**（36× `401 Invalid API Key`、36× `json parse error: timeout`、1× DNS）。**最后一次成功的 chat 是 2026-08-26T15:03Z**，此后 8/29、8/30、8/31 的 36 次调用全部报错。最后一次成功响应的 `finish_reason` 是 `length`。（**此处的成因判断在 §5.6 被实测推翻**：那 36 次 `json parse error: timeout` 不是输出截断，而是 30 秒全局 HTTP 超时。）

**影响**：`ResilientDistiller` 静默回退到 `HeuristicDistiller`，8-26 之后新增的 chunk 全是启发式产物；`innate inspect` 无任何 LLM 健康字段，故障可以无限期潜伏。

### P0-5 反噪规则结构性失效
**证据**：`kb/curate.rs:200-204` 的 `repeated_selected_unused` 归档条件是 `selected_count >= 10 AND used_count = 0 AND confidence < repeat_select_conf_max(0.5)`；而 `kb/evolve.rs:335` 蒸馏 chunk 的**初始置信度是 0.55**。实测满足「被选 ≥10 次且从未使用」的 chunk 有 **59 条，其中 48 条（81%）因 confidence>0.5 逃过归档**。
典型：`9f9e6c41` 被选 **188 次、使用 0 次、conf 0.54**，内容是一条「某项目重建置为等待执行状态…未做任何代码改动」式的会话状态汇报——不是程序性知识。

**影响**：噪声 chunk 永久驻留在召回结果里，直接推高 `selected_unused_rate=0.78`。

### P1-6 治理闸门堵死
459 条 pending、最老 73 天、7 日晋级 2 条。晋级要求 `promote_used_success_min=2 AND promote_confidence_min=0.6`，而全库 `used` 事件总共 381 次 → 绝大多数 pending 在数学上不可能晋级。

### P1-7 召回被长文本与「状态汇报」类 chunk 霸榜
`selected_unused_rate 0.78`、`MRR 0.494`。800-2k 字节的 52 条 chunk 人均被选 65.7 次（是 300-800 桶的 6 倍），使用率反而更低（0.025 vs 0.040）——**典型的长文本余弦长度偏置**。Top5 常选不用 chunk 全部是项目评估/会话总结类长文。
本次会话实证：UserPromptSubmit 召回 5 条，其中 2 条属于另一个无关业务项目的文档写作记录，与「回顾 innate 数据库」毫无关系。

### P1-8 每次用户提问阻塞约 2.1 秒
`hook_recall` p50 **2,176 ms**（其中远程 embedding p50 2,039 ms），最坏 12.2 s；10 次失败平均 **19,190 ms**。SessionStart + UserPromptSubmit 双钩子 → 每会话至少 2 次阿里云 embedding 往返。SessionStart 无 prompt，只能做泛化召回，本次实测 4 条命中率很低。

### P2-9 可观测性自身有洞
- `operation_runs` 中 2,379 条 recall/hook_recall 的 `trace_id` **全为 NULL** → ops 无法与 trace/outcome 关联。
- `by_dimension.agent` 只有 `(null)`：hook 通道 2,086 条 `agent_coverage=0.0`（install 未给 Stop/prompt hook 注入 `INNATE_AGENT`）。
- `task_success_rate=1.0` 是空指标：`task_fail` 事件数为 **0**，只记成功。
- `avg_retrieved=0.0`：`retrieved` 事件从未写入。
- `inspect` 的 params 只打印 5 个 `recall.*`，`w_lexical/w_confidence/anti_trigger_penalty` 等看不到。

### P2-10 存储与清理欠账
7,001 行已 compact 的空壳 episodic_log、3,912 行 daemon 死行、18.6 MB 的 operation_runs、5.9 MB 未 checkpoint 的 WAL、10.6 MB 六月旧备份、无保留策略的 `processed_events`（12,939 行）。

### P2-11 三层模型里两层零流量
`appraise` 调用 0 次、`verdict_log` 0 行、sparks 0、`origin='installed'` 0 条——「技能」与「直觉」两层在真实使用中从未跑起来。

## 5.2 两处刻意偏离原方案

**B3 没有做「启发式失败探测」。** 原计划写的是「Stop payload 含错误/中断信号时写 task_fail」。实际核查后 Stop payload 里**没有可靠的失败信号**——把「工具报错」或「用户打断」当作任务失败是猜测，而猜出来的 outcome 会直接写进 confidence EMA，正是 `hook.rs` 原有注释警告的事。因此只做了三件确定的事：确认 `record(outcome="fail")` 的写入链路完好（`usage_trace.task_fail` + 负向 confidence evidence）；把「失败也要记」写进 hook 注入文案和 `SKILL.md`（两份副本已同步，`cmp` 通过）；让 `task_success_rate` 在零 fail 样本时显示 `null` 而不是伪装的 1.0。**真正的 fail 信号只能来自 agent 主动 record**，这一项要靠几天后的数据验证文案是否奏效。

**D5（operation_runs 采样）不做。** A1 落地后 evolve/curate 从每天约 1,300 次降到约 288 + 24 次，采样要解决的存储问题已经消失；而采样本身会**减少**可观测性，与本轮目标相反。`metrics.retain_days=30` 的保留策略实测有效（表大小自然收敛）。

## 5.6 更换 api_key 后的实测：推翻 §2 P0-4 的成因判断

换上可用 key 后 401 消失，但调用改为**卡满 30 秒后失败**（`latency 30007ms`，报 `LLM response parse error: json: timeout: global`）。逐级实测该端点：

| 场景 | completion tokens | 耗时 |
|---|---|---|
| 极短 prompt | 25 | 3.7 s |
| 蒸馏 prompt（小） | 1755 | 69.4 s |
| 蒸馏 prompt（中） | 421 | 25.2 s |
| 蒸馏 prompt（大） | 414 | 19.4 s |

**耗时与 prompt 长度无关，与输出 token 数线性相关——该模型约 25 tokens/秒。** 而 `HTTP_TIMEOUT` 是 30 秒，任何超过约 700 token 的回答都会被拦腰截断，ureq 报出的 `json: ... timeout` 读起来像 JSON 格式错误，实际是秒表。

所以 §2 P0-4 里「36 次 parse error 是 `finish_reason=length` 截断」的判断**是错的**——真因是这个 30 秒超时，而且它早于本轮改动就存在（原 `max_tokens=800` 在 25 tok/s 下就已经需要约 32 秒，本就超限）。上一轮把 `max_tokens` 提到 2000 反而扩大了触发面。

**修法**：超时按调用类型拆开（`llm.rs`）。

- `HTTP_TIMEOUT_EMBEDDING = 30s` —— embedding 在召回热路径上，慢了就该降级到 lexical 通道，不该让用户等。
- `HTTP_TIMEOUT_CHAT = 180s` —— chat 只用于蒸馏与 opt-in rerank，都是后台、可容忍延迟的路径，从不挡在用户面前。过早放弃的代价是蒸馏静默退化成启发式兜底，比多等一会儿贵得多。
- `INNATE_HTTP_TIMEOUT_MS` 对两者都仍然生效（recall hook 用它把自己的 embedding 预算压到 2.5 秒）。

**验证**（真实飞轮一轮）：`recall → record(outcome=ok, output_summary) → evolve` 得到 `distilled: 2`，产物是真正的 LLM 抽象结果而非兜底拷贝，`distill_provider=openai/mimo-v2.5-pro`。

**附带发现（不修）**：`mimo-v2.5-pro` 在 **rerank** 这类比较型任务上会产出 `reasoning_content`，把 2000 token 预算烧光导致 `content` 为空、`finish_reason=length`。蒸馏 prompt 实测 `reasoning_tokens=0`、375–960 token 即完成，不受影响。rerank 本就是 opt-in、hook/daemon 从不调用、失败自动回落到 fused 排序，因此按「只解决已明确的需求」不额外处理；真要常用 rerank 再按数据调 `max_tokens`。

**注意 `llm_health.degraded` 的滞后**：它按 24 小时窗口算成功率，窗口里还压着修复前的 59 次失败，所以短期内仍显示 `true`。判断「现在是否可用」看 `by_kind.chat.last_ok_ts` 是否为当前时间即可。
